# Needledrop — briefing for agents

Read this before touching the repo. Update the **Progress** section as the last step of any task.

## What this is

Needledrop is a daily song-guessing game in the style of Heardle: you hear a sliver of a song, guess it, and each wrong guess or skip unlocks a longer clip. The music is Deezer's free 30-second previews. The repo and Rust crate are named Needledrop (`needledrop-server`).

Decisions already made, and why:

- **The server is authoritative.** The browser never sees the answer's Deezer ID, title or preview URL until the game is over. A client-only game would leak the answer through the network tab.
- **The server sends only the audio unlocked so far.** If the full preview reached the browser, anyone could play all 30 seconds. The server cuts the MP3 to the current clip length on every request.
- **No accounts.** Everyone plays without logging in and each browser is remembered by an encrypted, HttpOnly cookie that holds a random anonymous player ID and nothing else. The games are in the server's database under that ID, and the stats are worked out from them. Accepted limit: clearing cookies or using a private window gives a fresh player.
- **Daily mode: four sections, one song each per day, the same for everyone.** General, Pop, Rock and Hip-hop are four separate seven-attempt games a day, each with its own song of the day drawn from the curated song database (`pick.rs` decides, `daily.rs` checks, stores and loads). The day is the server's day: the real UTC date plus a stored offset that the admin can move (Simulate next day, Reset to day 1). The agreed requirements are in **Roadmap** below, and all of it is built (tasks 10–14).
- **Random mode: one song after another, without limit.** A fifth tab at `/random` (task 22, agreed with the owner on 2026-10-01). The game is the daily one, played against a song drawn from the whole pool: never one of the day's four picks, so random mode cannot give a daily game away, and not one of the player's last 50 songs while anything else is left. A song is over when it is guessed or the seven tries are used (there is no give-up shortcut, by the owner's choice); then the player asks for the next. The server keeps one random game per player (`random.rs`): the song, the tries, the session's score and the two things that outlast a session, the longest run and the recent songs. **A session is the player's and ends after 30 minutes without a move** (`random::SESSION_IDLE`): every tab of the browser opens the session that is under way, and the first visit after it has ended starts from scratch. (Task 23, the owner's change on the day it was built: at first a session was one browser tab.) **The player can filter it by genre** (task 24, asked for by the owner on 2026-10-03): the session draws from a pool, which is every song ("All", the default) or only the songs tagged Pop, Rock or Hip-hop. A change made in the middle of a song applies from the next song drawn, by the owner's choice: the song in progress is never replaced, so changing the genre is not a way out of it, and the session, run and score carry on across genres.
- **Ladder: 0.1 / 0.3 / 1 / 3 / 8 / 16 / 30 seconds — seven attempts.** The first clips are deliberately tiny; that is the game.
- **A guess is correct when the normalized title and primary artist both match.** Remasters, live cuts and album variants of the same song have different Deezer IDs, so comparing IDs would reject right answers.
- **Guesses must be picked from autocomplete.** The client sends a track ID, and the server looks up the title and artist itself, so a client cannot forge them.
- **Rust server (axum), Svelte 5 + Vite client, Nix dev shell.** Nothing needs to be installed globally: the flake provides `cargo`, `rustc`, `pnpm`, `just` and the rest.
- **TLS via rustls, no OpenSSL**, so the dev shell needs no system libraries.

## Layout and architecture

```
browser ─▶ Vite dev server 127.0.0.1:4811 (Svelte SPA) ── /api ─▶ axum server 127.0.0.1:4810 ─▶ api.deezer.com / preview CDN
                                                                      │
                                                                      └─ data/  (cached mp3 + track JSON, cookie key, needledrop.db)
```

Both processes speak plain HTTP on loopback. Vite proxies `/api` to 4810, so `http://127.0.0.1:4811` is the whole app in development.

For development under a public hostname, put a TLS-terminating reverse proxy in front: `/` → 4811, `/api/` → 4810, forwarding `X-Forwarded-Proto` (see the cookie notes below). Set `ND_PUBLIC_URL` to that HTTPS origin for both processes. The server puts it in the user agent it shows Deezer; `web/vite.config.ts` uses it for `server.allowedHosts` and the HMR websocket (`wss` on 443 for HTTPS). With it set, hot reload connects for a page opened through that address; without it, both processes work for plain localhost. Set `ND_BIND` if the API listens somewhere other than `127.0.0.1:4810`; Vite uses it for its development proxy. The production Nix deployment (the host's `nixos/needledrop.nix`, outside this repo) builds the SPA and serves it directly from nginx. Of `/api/` it forwards only a list of routes to the Rust service, each with its methods: the eleven the game calls (the daily game's six and random mode's five) and `/api/health`, plus `/api/admin/*` behind Authelia. **A route added to the server is not public until it is added to that list**; anything else under `/api/` gets a 404 from nginx in the API's error format. nginx also limits searches (2 per second, 10 extra at once), guesses (1 per second, 14 extra at once; the daily ones and random mode's share the limit) and random mode's draws, `start` and `next` (1 per second, 10 extra at once; a change of genre is a `start` and counts), per connecting address, and answers the ones beyond that with 429 `{ "error": "rate_limited", "message": … }`, which the page shows like any other failed search or move.

```
flake.nix, flake.lock   dev shell: cargo, rustc, clippy, rustfmt, rust-analyzer, bacon, nodejs_24, pnpm, just
justfile                recipes (below)
bacon.toml              the `server` job `just dev` uses: restarts the server when server/src or Cargo.toml changes
server/                 Rust crate `needledrop-server`
web/                    Vite + Svelte 5 + TypeScript SPA (plain Vite, not SvelteKit), pnpm
scripts/                add-playlist.mjs: fills the pool from Deezer playlists through the admin API (Node, no dependencies; see below)
data/                   default runtime state, git-ignored, created by the server: audio/, secret.key, needledrop.db
```

| `daily.rs` | The day and its songs. `Clock` (the real time, and the real date read off it; `Clock::utc()` or a test's own) and `Daily::days()` / `today()`: the real UTC date plus the offset in the store. `Daily::now()` is the real time, which the offset does not move. `Daily::song(day, section)` → `Playing { day, section, track_id, song: Arc<Song> }` (`Song` has `meta` for matching, `answer` for the reveal, the parsed `mp3`): the stored pick with its song from memory when both are there; otherwise, under one lock, the sections ahead in `PICK_ORDER` get their turn, then this one is drawn (`pick::choose`), **loaded, and only then stored** (`Store::save_pick`). Loading is the preview check: memory, else `data/audio/<track_id>.mp3` + `.json`, else `/track/{id}` and the preview download, parsed before it is cached. A track Deezer has no preview for (not readable, no preview URL, a body that is not an MP3, no such track) is marked `preview_failed_on = day` and another is drawn; any other failure stores nothing, returns the error and keeps further Deezer requests away for 10 s. Up to 32 parsed songs stay in memory: the day's four, and the songs random mode's players are on. `load_song(track_id)` loads any track the same way (memory, disk, Deezer, the same pause after a failure), and `random_song(day, section, recent)` is random mode's draw from that section's pool with the same preview check: it first gives the sections without a pick their turn, so that all four of the day's songs are known and left out, then draws (`pick::draw_random`), loads, marks a track without a preview and draws again; it stores nothing about whose song it is. `reroll(sections)`, `next_day()` and `reset(launch)` change the day or its picks under the write side of a lock; `stands(&playing)` gives a request the read side after checking the stored pick is still the track it holds. `warm(day)` settles all four. Its error messages name tracks, so they go to the log, never to a client. |
| `game.rs` | Pure logic: the ladder, `GameState` (one player's game on one day; what the store keeps) and its transitions, `day_number`, and `normalize_title` / `normalize_artist` (lowercase, strip diacritics, use `title_short`, drop bracketed / "feat." / "- remaster" suffixes, strip non-alphanumerics). Match = normalized title **and** primary artist equal (`is_match`, `TrackMeta::match_key`). It does not care how the track was chosen, who is playing or in which section, so later modes can reuse it. |
| `routes.rs` | `AppState` (the Deezer client, `Daily`, the `Arc<dyn Store>`, the move locks, the launch date and the cookie key; `deezer()`, `store()`, `move_locks()`, `daily()`, `launch_date()`, `today()`, `now()`, `song(section, day)`, `warm_up()`), `router(state)` (the game's routes, `random::routes()`, `player::clear` and `admin::routes()`), the game's handlers, `ApiError`, `store_failed` (logs a `StoreError`, answers 500 `internal`) and `daily_failed` (`DailyError` → `no_song`, `internal` or `upstream`). `today` is the overview behind the tabs; it reads and never picks. `show_game`, `play_clip` and `make_move` take the section and are what the three per-section handlers call. `standing_song` fetches a section's song and holds `Daily::stands` while the games are read, so a response is about one song. `History` is a player's games in a section, today's apart from the rest; `DailyView::new` is the only place the answer is handed out. A guess's metadata is resolved server-side from `trackId` (`Deezer::track_meta`: the cache filled by searches, else `/track/{id}`), before the locks are taken. |
| `player.rs` | Who is playing. The player cookie (`known_player(jar)` → `Option<PlayerId>`, `remember(jar, player, headers)`), `MoveLocks` (64 striped async locks; `lock(&player)` is held across the read, the move and the write of a move, and by Clear my data), the `DELETE /api/player` handler `clear`, and the cookie key (`session_key`). |
| `random.rs` | Random mode. The pure state first: `RandomGame` (one per player; what the store keeps) with `start(previous, track_id, pool, day, now)` (a new session: score zero; the longest run, the recent songs and the round carried over; the pool is the caller's to decide), `next(track_id, day, now)` (only from a finished song; keeps the pool), `skip(now)` and `guess(answer, guessed, now)`, which take a song that ends into `played`, `won`, `run` and `best_run`, `pool()` and `draw_from(pool)` (the `Section` whose pool the next songs are drawn from; changing it changes nothing else and is not playing), and `is_over(now)`: the session was last played (`active_at`: its start, a move or a next) `SESSION_IDLE` ago, 30 minutes, or more. Then `routes()` and the five handlers under `/api/random` (see **Random mode API**), and `RandomView`, the only place random mode hands out an answer. A session that is over is answered like no game at all. Drawing and loading are `Daily`'s (`random_song`, `load_song`). |

### API

All JSON keys are camelCase. The frontend is built against exactly this; do not rename fields.

| Route | Behaviour |
|---|---|
| `GET /api/health` | `{"ok":true}`. |
| `GET /api/today` | The overview behind the tabs. 200 `{ day, number, sections }`: `day` is the server's day, `number` counts from `launch_date` (1 on that day), and `sections` has one entry per section in tab order (general, pop, rock, hip-hop): `{ section, status, attempts, song }`. `status` is the player's game there today (`playing` / `won` / `lost`; `playing` with `attempts` 0 is a game not started), `attempts` is the number of tries used, and `song` is `"picked"`, `"pending"` (not picked yet, but the pool has a candidate; the pick is made when the section's game is first asked for) or `"none"` (no song today). It reads and never picks, so it is fast, and `pending` means "probably". Nothing in it comes from a song. Sets or refreshes the player cookie. `Cache-Control: no-store`. |
| `GET /api/daily/{section}` | `section` is `general`, `pop`, `rock` or `hip-hop`. 200 `{ day, number, section, ladder, attempts, status, clipSeconds, answer, stats }`. `day` is the server's day, `number` counts from `launch_date` (1 on that day), `section` is the slug asked for, `ladder` is `[0.1, 0.3, 1.0, 3.0, 8.0, 16.0, 30.0]`, `attempts` is `[{"kind":"skip"} \| {"kind":"wrong","title","artist"}]`, `status` is `playing` / `won` / `lost`, `clipSeconds` is the clip length unlocked now (30 once finished). `answer` is `null` while playing and `{ title, artist, album, cover, link }` once won or lost (`cover` is the 500 px album cover, falling back to smaller ones; `link` is the deezer.com track URL). `stats` is the player's record in that section (below); it is there in every state. The first request of a day for a section makes its pick (and those of the sections ahead of it in the pick order), which can take as long as a few downloads. Sets or refreshes the player cookie; a browser without one is given a new ID. Stores no game: a game is written with its first move. `Cache-Control: no-store`. |
| `GET /api/daily/{section}/audio` | 200 `audio/mpeg`: `mp3.prefix(unlocked_ms)` of the game the player cookie leads to in that section, frames only, with `Content-Length` and `Cache-Control: no-store`. No `Accept-Ranges`; a `Range` header and any query string are ignored. Does not set the cookie. Without a cookie it is the 0.1 s clip. |
| `GET /api/search?q=` | 200 `[{ id, title, artist, album, cover }]`, at most 8. `q` is trimmed (and cut at 100 characters); fewer than 2 characters → `[]` without calling Deezer. Otherwise 25 results are fetched from Deezer `/search/track`, tracks with a blank title dropped, de-duplicated by `TrackMeta::match_key()` keeping the first of each, then cut to 8. `title` is Deezer's full `title`, `cover` is `album.cover_small` (56 px, may be empty). |
| `POST /api/daily/{section}/guess` | JSON `{ "trackId": 123 }` or `{ "skip": true }` → 200 with the body of `GET /api/daily/{section}` after the move (the `stats` include a game this move finished), and the cookie. A correct guess sets `won` and adds no attempt. The game is stored. Moves of one player are made one at a time, so several sent at once each cost a try. Works without a cookie: that is the first move of a new player. |
| `DELETE /api/player` | Clear my data. 204 with no body. Deletes every game stored for the player in the cookie, in every section and today's included, and their random game with its longest run, and sets the cookie to a new ID. Without a cookie nothing is deleted and an ID is still issued. The day's songs do not change. The old ID is not revoked: a copy of the old cookie is a player without games. `Cache-Control: no-store`. |

`stats`, always for one player in one section, derived from the stored games on every request (nothing is kept as a counter, so a deleted game takes its share with it):

| Field | Meaning |
|---|---|
| `played` | Finished games, won or lost. A game that was started and not finished is not counted, on any day. |
| `won` | How many of those were won. |
| `winPercent` | `won` of `played` as a whole number from 0 to 100, rounded to the nearest (a half goes up); 0 when nothing has been played. |
| `currentStreak` | Consecutive days won, ending today, or yesterday while today's game is not finished. A loss, an unfinished game on an earlier day or a day without a game ends it. |
| `bestStreak` | The longest run of consecutive won days so far; never less than `currentStreak`. |
| `guessDistribution` | Seven numbers: the wins on the first try, the second, … the seventh. A win after `n` recorded attempts was on try `n + 1`. They add up to `won`. |

"Today" is the day of the game in the response: the server's day. Games dated after it (they exist when the admin has moved the clock back without a reset, or the machine's clock went back) are left out until their day comes.

Errors are `{ "error": "<code>", "message": "<sentence>" }`. The messages are fixed text, safe to show the player.

| Status | `error` | When |
|---|---|---|
| 400 | `bad_request` | Guess body that is not JSON, not `application/json`, or names both or neither of `trackId` / `skip`. No turn is used. |
| 404 | `unknown_track` | Deezer has no track with that `trackId`. No turn is used. |
| 404 | `not_found` | No such route, or a section slug that is not one of the four. The routes from before the sections are gone since task 13 and answer this too: `/api/daily`, `/api/daily/audio` and `GET /api/daily/guess` (the last two are read as section slugs, which they are not). A `POST` to `/api/daily/guess` gets axum's 405 with an empty body, as any method a route does not have. |
| 404 | `no_song` | The section has no song today: its pool is empty, or everything in it plays in another section today or failed the preview check today. Answered by the section's game, audio and guess routes; the UI shows it as "No song today". Not something a retry mends (adding a song, or a re-roll elsewhere, can). |
| 409 | `finished` | A move on a game that is already won or lost. Checked before anything is looked up, and again when the move is made: of several moves sent at once, those that come after the one that ends the game get this. |
| 409 | `changed` | The section's song was replaced (an admin re-roll or reset) while the request was under way. A move is not made and nothing is stored; the client should load the game again. |
| 502 | `upstream` | Deezer failed or this server's request budget is used up (search, guess lookup), or the section's song could not be picked or loaded because Deezer did not answer (game, audio, guess). The pick is tried again by a later request, at most every 10 s; no song is skipped for it. |
| 500 | `internal` | The store failed (reading the day offset or the picks, reading or saving a game, clearing a player's data, the admin routes); the reason is in the log. |

**Anti-leak rule:** while a section's game is `playing`, nothing sent to the client may contain that section's answer — its Deezer ID, title, artist, album, cover or preview URL — JSON, headers, cookie and error messages alike. `GET /api/today` never contains any. The tests of `routes` and `player` assert it on playing-state responses, headers included; keep those assertions when adding routes. The cookie cannot leak: all it holds is the player ID. Finishing one section reveals that section's answer only; no song is the answer in two sections on one day, so it tells nothing about the others. The rule holds for random mode's routes in the same way (the song a player is on is theirs alone, and its `round` is a counter that says nothing about the track), and a finished random song reveals none of the day's answers, because the day's picks are never drawn there.

Cookie: named `nd_player`, holding the anonymous player ID — 32 lowercase hexadecimal characters, 128 random bits from `rand`'s OS-seeded generator — and nothing else, encrypted with axum-extra's `PrivateCookieJar`, so a client can neither read it nor make a cookie for an ID of its choosing. Attributes: `HttpOnly; SameSite=Lax; Path=/; Max-Age=34560000` (400 days, the most a browser keeps), plus `Secure` when the request has `X-Forwarded-Proto: https`. A TLS-terminating reverse proxy in front must send that header (in nginx, `proxy_set_header X-Forwarded-Proto $scheme`). On plain HTTP (the Vite dev server on localhost) the cookie is not `Secure`, or the browser would drop it. It is set again by every `GET /api/today`, every `GET /api/daily/{section}` and every move, so it only runs out for a player who stays away for 400 days. A cookie that is missing, does not decrypt or does not hold a well-formed ID is a new player: the overview, a section's game, a move and Clear my data then issue a new ID. The audio route never sets it. The old `gts_player` and `gts_daily` cookies are not read; existing browsers receive a fresh player ID under `nd_player`.

Games: stored per player, section and day as `game::GameState` — `{"day":"2026-10-01","attempts":[{"kind":"skip"},{"kind":"wrong","title":"…","artist":"…"}],"status":"playing"}` — written by each move and never by a visit. No stored game for today means a fresh game. Stored titles and artists are cut to 80 characters and 160 bytes, so a row is under 2.7 kB. A stored game that cannot be read (not JSON, an impossible state such as `playing` with seven attempts, a game filed under another day than its own) is logged and counts as not there, so the player gets a fresh game for that day instead of an error, and the next move replaces the row. Unlocked clip length = `ladder[attempts.len()]`. A re-roll deletes every player's game for that section and day, and a reset every game.

Picks: one stored row per day and section (`store::Pick`), written once the song has been loaded, so a pick that stands can be played. The answers of a day are in the log (`picked the section's song for the day … title=… artist=…`) and in `GET /api/admin/state`.

Cookie key: 64 random bytes written as 128 hexadecimal characters in `<data_dir>/secret.key`, generated on the first start with mode 0600 and reused after that, so cookies survive restarts. A malformed key file stops the server at startup; delete the file to get a new key. A new key means no browser's cookie can be read any more: everyone becomes a new player, and the games stored under the old IDs stay in the database with nobody able to reach them.

### Random mode API

One endless game per player, under `/api/random` (task 22). The conventions are those of the daily routes: camelCase keys, the same error body with fixed messages, `Cache-Control: no-store` on every response, and the anti-leak rule.

The view, the body of every successful response except the audio: `{ round, ladder, attempts, status, clipSeconds, answer, run, bestRun, played, won, pool }`. `ladder`, `attempts`, `status`, `clipSeconds` and `answer` are exactly those of `GET /api/daily/{section}` (`answer` is `null` while the song is being played). `round` goes up by one with every song drawn for the player, across sessions (1 for the first); it names the song a move is for and says nothing about the track. `run` is the wins in a row in this session (a lost song sets it to 0), `played` and `won` are the songs finished and won in this session, and `bestRun` is the longest run the player ever had, the one number that outlasts a session. `pool` is the pool the session's **next** songs are drawn from, as a section slug: `general` (every song, the default), `pop`, `rock` or `hip-hop`. It is the player's own choice and not necessarily where the song on screen came from, so it gives nothing of that song away. There is no `day`, `number`, `section` or `stats`.

**The pool** (task 24) is stored with the session, so every browser tab sees the same choice, and it carries over to the player's next session like the longest run. It is chosen with `POST /api/random/start` and with nothing else: there is no route of its own, because the deployment forwards a fixed list. Choosing in a session that is going draws nothing: the song being played, its tries, the round and the score stay, and the next song is the first drawn from the new pool. Choosing is not playing: it does not extend the session.

**A session** is the player's, whatever browser tab it is played in. It is over when it has not been played for 30 minutes (`random::SESSION_IDLE`), where playing is a write: the session's start, a skip or guess that is made, a next. A look and a clip store nothing and do not count. The time is real time; the admin's day offset does not move it. A session that is over is answered exactly like no game (404 `no_game`) and nothing is written: the record stays, for the next start to carry the longest run, the recent songs and the round over from.

| Route | Behaviour |
|---|---|
| `GET /api/random` | 200 with the view of the song the player is on. 404 `no_game` when the player in the cookie has no session (no cookie, never started, cleared, wiped by a reset, or over). Refreshes the cookie on 200; never issues a new ID; stores nothing. |
| `POST /api/random/start` | The session to play in, and the pool it draws from. The body may name a pool: `{ "pool": "rock" }`, one of the four section slugs; no body, `{}` or `{ "pool": null }` is no choice. The content type is not looked at and other fields are ignored. A player whose session is still going is given it as it stands: nothing is drawn, so a second browser tab joins the session; without a choice, or with the pool the session has, nothing is written either, and another pool is stored (under the move lock) and is all that changes. Otherwise a new session begins: the song the player was on is left behind in whatever state (it counts for nothing), `run`, `played` and `won` start at zero, `bestRun`, the recent songs and the round carry over, and a song is drawn from the chosen pool, or without a choice from the pool of the player's stored record, or from `general` for a player without one. Two starts that both find the session over end up in one session: the second is given the first's, with its own choice of pool applied to it. → 200 with the view. Sets the cookie; a browser without one is given a new ID. The one random route that works without a cookie. |
| `GET /api/random/audio` | 200 `audio/mpeg`: `mp3.prefix(unlocked_ms)` of the song the player is on, as the daily audio route (frames only, `Content-Length`, no ranges, any query string ignored). 404 `no_game` without one. Never sets the cookie. |
| `POST /api/random/guess` | JSON `{ "round": n, "trackId": 123 }` or `{ "round": n, "skip": true }` → 200 with the view after the move. A correct guess sets `won` and adds no attempt; a song that ends is taken into the score. Moves of one player are made one at a time. |
| `POST /api/random/next` | JSON `{ "round": n }`, the song being left behind → 200 with the view of the next song of the session, drawn from the session's pool. The score goes on. |

**The draw** (`start` and `next`): the session's pool (every song, or the songs tagged with the chosen genre), without the songs the four sections play on the server's day and without songs whose preview failed the check that day. Among those, a random one that is not among the player's last 50 (`random::RECENT_SONGS`, each track once); when all of them are recent, the one played longest ago. The day's missing picks are made first, as a daily request would make them, so that all four are known; a section that cannot be picked does not stop the draw. The drawn song is loaded before it is stored, and a track without a preview is marked `previewFailedOn` and another is drawn, as the daily pick does.

| Status | `error` | When |
|---|---|---|
| 400 | `bad_request` | Guess: a body that is not JSON, is not `application/json`, has no whole-number `round`, or names both or neither of `trackId` / `skip`. Next: no whole-number `round`. Start: a body that is not empty and not a JSON object, or a `pool` that is not one of the four slugs. Checked before the cookie is looked at. Nothing changes. |
| 404 | `no_game` | Get, audio, guess, next: the player has no session: no random game at all, or one that has not been played for 30 minutes. The client starts a session. |
| 404 | `unknown_track` | Guess: Deezer has no track with that `trackId`. No try is used. |
| 404 | `no_song` | Start (of a new session), next: nothing can be drawn from the session's pool (it is empty, or everything in it plays in a section today or failed the preview check today). The stored game is not changed, so after a next the player can choose another pool with `start` and ask again. A choice made in a session that is going draws nothing and so never gets this, even for a genre without songs. |
| 409 | `changed` | Guess or next whose `round` is not the song the player is on: another browser tab has moved on to the next song. Checked before `finished`. Nothing changes; the client loads the game again. |
| 409 | `finished` | Guess on a song that is already won or lost. |
| 409 | `unfinished` | Next while the song is still being played. |
| 502 | `upstream` | Deezer failed or the request budget is used up: the guess lookup, or loading the song (the one drawn, or the one the player is on after it left memory and the disk cache). |
| 500 | `internal` | The store failed. |

Random games: one stored record per player (`random::RandomGame`, as JSON, with `active_at`, when it was last played, in seconds since the Unix epoch; a record without it reads as a session long over; and with `pool`, a section slug, where a record without it reads as `general`), written by a start, a move, a next and a change of pool, never by a look. The pool is inside that JSON, so it needed no migration: the schema is still version 4. Clear my data deletes it, and Reset to day 1 deletes all of them; a re-roll and the next day leave them alone. A record that cannot be read counts as not there.

### Admin API

Complete since task 12: the clock, today's picks and the re-roll, and the song pool with its search. **These routes are not protected**, and the anti-leak rule does not apply to them: `GET /api/admin/state` shows the day's answers. The conventions are the ones above: camelCase keys, the same error body with fixed messages, and `Cache-Control: no-store` on every response, errors included.

The state is `{ realDay, offset, day, number, sections }`: `realDay` is the real UTC date, `offset` the stored day offset (negative when the server's day is behind), `day` the server's day (`realDay` plus `offset`), `number` the day number (1 on `launch_date`), and `sections` has one entry per section in tab order: `{ section, status, pick }`. `status` is `"picked"` (the song is picked and loaded), `"none"` (no song today) or `"unavailable"` (Deezer did not answer, so the pick could not be made or its song could not be loaded; later requests try again). `pick` is `{ trackId, title, artist }` or `null`; with `unavailable` it is the standing pick named from the pool (blank title and artist if the song has left the pool), or `null` when there is none yet.

A song row is `{ trackId, title, artist, album, genres, previewFailedOn }`. `title` is Deezer's full title. `genres` is an array of the slugs `pop`, `rock`, `hip-hop`, always in that order, and empty for a song that is in the General pool only. `previewFailedOn` is `"YYYY-MM-DD"` or `null`: the day the daily pick last found the track without a preview. It is cleared the next time the song is picked and plays.

| Route | Behaviour |
|---|---|
| `GET /api/admin/state` | 200 with the state. **It makes the picks that are missing**, exactly as a player's first request of the day would (so it can take as long as a few downloads): the page exists to show the day's songs. A section that fails does not fail the others or the response. |
| `POST /api/admin/reroll` | Body `{ "section": "pop" }` (any of the four slugs) for one section; no body, `{}` or `{ "section": null }` for all four. The content type is not looked at. → 200 with the new state. Each named section loses its pick for the server's day and **every player's game there that day**; the state in the response then picks again, as a day's first request would. The replaced song is left out of the draw when the section has another candidate; songs the other sections play today are never drawn. With a single candidate the same song comes back, and the games are deleted all the same. If Deezer is down the section shows `unavailable` and the pick is made by a later request. |
| `POST /api/admin/next-day` | Simulate next day: adds one to the offset. → 200 with the new state (which makes the new day's picks). Nothing is deleted; every player is on the new day from their next request. |
| `POST /api/admin/reset` | Reset to day 1: deletes every game, every random game and every pick and sets the offset so that the server's day is `launch_date`. The song pool, `previewFailedOn` included, is kept. → 200 with the new state. |
| `GET /api/admin/songs?q=&genre=&failed=&offset=&limit=` | The pool, searched and cut by the server, so the page never receives all of it. Every parameter is optional. `q`: trimmed and cut at 100 characters, split on whitespace; every word has to be found, ignoring case and accents, in the song's title, artist, album or track ID (a part of a word is enough); empty is no filter. `genre`: `pop`, `rock` or `hip-hop`, only songs with that tag. `failed`: `true` for only the songs with a `previewFailedOn`. `offset`: default 0. `limit`: default 25, anything above 100 is 100, and 0 asks for the counts alone. → 200 `{ total, offset, limit, songs, counts }`: `total` is how many songs match the filters, `songs` the song rows of that page, sorted by artist, then title, ignoring case, then track ID; `offset` and `limit` are the ones applied; `counts` is `{ all, pop, rock, hipHop, previewFailed }` for the whole pool whatever the filters. An offset past the end is an empty `songs` with the right `total`. |
| `POST /api/admin/songs` | JSON `{ "trackId": 123, "genres": ["pop", "hip-hop"] }` → 200 with the stored song row. `genres` may be left out, `null` or `[]` (no tags); a slug given twice counts once. A song already in the pool only has its genres replaced: no Deezer request is made, and its stored title, artist, album and `previewFailedOn` are kept. Otherwise the track is fetched from Deezer (`/track/{id}`, one request against the budget) for its title, short title, artist and album, and stored. **It never checks `readable` or `preview`:** a track without a preview is added like any other. Other fields in the body are ignored. The response does not say whether the song was new. |
| `DELETE /api/admin/songs/{trackId}` | 204 with no body. The song and its genre tags are gone; adding it again starts from nothing. |
| `GET /api/admin/search?q=` | 200 `[{ id, title, artist, album, cover, playable, inPool, genres }]`: the rows of the player's search plus `playable` (`readable` and a non-empty `preview`, read from the search result itself, so there is no request per row), `inPool` (this very track is in the pool already, so adding it would only replace its genres) and `genres` (the genres it has there, possibly `[]`; `null` when it is not in the pool). The `q` rules are those of `/api/search`, and both searches share one cached Deezer answer of 25 tracks, but here every release is listed, in Deezer's order, up to all 25. Tracks with a blank title are dropped. |

| Status | `error` | When |
|---|---|---|
| 400 | `bad_request` | Add: a body that is not JSON, is not `application/json`, has no whole-number `trackId`, or names a genre that is not one of the three slugs. Nothing is looked up or changed. Pool list: a parameter that cannot be read (a `genre` that is not one of the three slugs, an `offset` or `limit` that is not a whole number of zero or more, a `failed` that is not `true` or `false`). Remove: a track ID in the path that is not a whole number. Re-roll: a body that is not empty and not a JSON object, or whose `section` is not one of the four slugs; nothing is re-rolled. |
| 404 | `unknown_track` | Add: Deezer has no track with that ID, or the track has a blank title. |
| 404 | `unknown_song` | Remove: the pool has no song with that track ID. |
| 502 | `upstream` | Add of a song that is not in the pool yet, or search: Deezer failed or the request budget is used up. Nothing is added. |
| 500 | `internal` | The store failed, or the day offset leads outside the calendar. The admin search needs the store too (for `inPool`), unless the query is too short to search for. |

A method a route does not have (`GET /api/admin/songs/123`) gets axum's 405 with an empty body, as on the player's routes. Adding or removing a song never changes a pick that stands: a song removed from the pool stays today's song where it was picked.

### Frontend (`web/src/`)

The midnight listening-room UI (task 6), with the four sections as tabs since task 13, the admin page at `/admin` since task 14, and random mode as a fifth tab at `/random` since task 22. The durable visual contract lives in `DESIGN.md`; this is where things live.

Every other address mounts `App.svelte` with the tab it names, after rewriting an unknown or oddly written address to the tab's own (`/nonsense` → `/`, `/Pop/` → `/pop`, `/Random/` → `/random`; `history.replaceState`, query and hash kept). Nothing about the session is kept in the browser: whether one is under way, and which pool it draws from, is the server's to say.

The fields the components read are always those of `tab`, the one on screen: `view` (a `Daily` or a `RandomSong`), `loading`, `loadError`, `noSong`, `submitting`, `moveError`, `notice`, `info`, and the derived `status`, `finished`, `attempts`, `ladder`, `answer`, `stats` (a section's record; `null` on Random), `song` and `score` (the random song and its session's score; `null` on a section), `pool` (the pool random mode's next songs come from: the random song's; without a song, the one whose draw found nothing on this page; else `general`), `random`, `scene` (which game is on screen: a section on a day, or one random round), `turn`, `lastTurn`, `clipSeconds`, `nextClipSeconds`, `totalSeconds`, `slots`. Page-wide: `day`, `number`, `tabs` (five `{ tab, state }`; Random's is always `endless`), `playing`, `clipLoading`, `clipError`, `fresh` (the move just made ended the game on screen, so the reveal runs; cleared by leaving the tab), `clearing`, `drawing` (random mode's next song is on its way), `busy`. Methods: `open(tab)` (page load: the overview and the game, in parallel), `select(tab)` (a tab), `load()` (the retry buttons), `refresh()` (the browser tab became visible), `play()`, `stop()`, `toggle()`, `skip()`, `guess(track)`, `next()` (random mode: the next song), `choosePool(pool)` (random mode: the genre of the songs to come), `clipSettled()`, `progress()`, `clearData()`. What it does with the server's answers:
  - **Tabs.** `tabs` comes from the overview and from every game response, whichever is newer for a section (a per-section version counter decides), so a move updates its tab without asking the overview again. An overview that fails leaves the tabs `unknown`; the game on screen still loads and fills in its own tab.
  - **Switching.** `select` stops the clip and drops it (the player holds one buffer, so the clip is fetched again on every switch). A section seen before is shown at once and quietly asked about again; a new one shows "Loading today's song…" until its game arrives.
  - **404 `no_song`** on a load or a move: the section shows "No song today" and its tab the dash. An overview entry with `song: "none"` shows it at once when the tab is opened; the request is still made and has the last word. "Check again" asks again.
  - **409 `changed`**: the section's game and the overview are fetched again and `info` says "The song in this section was changed, so that move did not count. The game starts again." **409 `finished`**: the game is fetched again, no error shown. Any other failed move is `moveError`, shown by the controls; the try is not used.
  - **A failed load** (502, 500, no network) is `loadError` with "Try again" when the section has nothing on screen, and `moveError` when a game is there.
  - **A `day` that is not the one on screen**, in any response: everything heard about the day is dropped (all four games, the tabs, the clip; the random game has no day and stays, with its clip when it is on screen), `info` says "The day has changed. This is today's game.", and the overview and the game on screen are asked for again. Answers still on their way from before are ignored (an epoch counter, and a request counter per section).
  - **Clear my data**: `clearData()` refuses while a move is on its way (a move answered after the deletion would set the old player's cookie again, with that game), calls `DELETE /api/player`, then drops everything (the random game too) and asks again. A failure returns the sentence and changes nothing.
  - **Random mode.** Opening the tab asks for the session under way (`GET /api/random`), and a 404 `no_game` starts one (`POST /api/random/start`): silently when nothing was on screen, and with the `info` line "That session ended after a while away. This is a new one." when a game was (a tab that becomes visible after a long absence, a move, a next). A second browser tab so opens the same session. A start counts as a move (`submitting`), so it is never sent twice and Clear my data waits for it. **A start waits for the overview and daily requests already on their way**: a browser the server has not met is given a player ID by every answer and keeps the one that arrives last, so a start sent beside them could store its game under an ID the browser then loses. Moves and `next()` carry the `round`. 409 `changed`: the game is fetched again and `info` says "This song was changed in another tab, so that move did not count." 409 `finished` and `unfinished`: fetched again, nothing shown. 404 `no_song`: "No song to play" with "Check again", which repeats the start, or the draw when a finished song is still there. Another round arriving clears `fresh`, so the next song is put on without the reveal.
  - **The pool.** `choosePool(pool)` is a start that names the pool, so it follows a start's rules (it counts as a move, is never sent twice, waits for a new browser's first requests, and Clear my data waits for it). With a song being played, the view comes back the same but for `pool`: the same round and tries, so the clip is not fetched again and the record does not change. With a finished song, only the pool changes and nothing is drawn. Where "No song to play" is showing, the choice is also the retry: after it, the draw is asked for again (`next()` when a finished song is still there). If the session had ended while the page was open, the start begins a new one in that pool and the "That session ended…" line is shown (`sameSession` tells this from a tab that merely caught up). 404 `no_song` on the choice: "No song to play" naming that genre. Any other failure is the move-error line, and the picker shows the pool that stands. ## How to work here

Everything runs inside the dev shell: `nix develop`, or prefix single commands with `nix develop -c`. Flakes only see files git knows about, so `git add` new files before expecting Nix to see them.

| Recipe | What it does |
|---|---|
| `just dev` | Server with auto-reload (bacon) and the Vite dev server together. Ctrl-C stops both. |
| `just server` | Server only, no auto-reload. |
| `just web` | Vite dev server only. |
| `just test` | `cargo test`. |
| `just check` | `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check`, `svelte-check` + `tsc`, `vite build`. |
| `just build` | Release build of the server and the client bundle (`web/dist`). |
| `just fmt` | `cargo fmt`. |

All recipes run from the repo root, so the default `data/` resolves there.

- **Ports:** `4810` Rust API (`ND_BIND` overrides), `4811` Vite. Both bind `127.0.0.1` by default.
- **Before a commit, both must pass:** `nix develop -c just check` and `nix develop -c just test`.
- **Real-preview test fixture:** `mp3::tests::real_preview_fixture` checks the frame walker against `server/tests/fixtures/preview.mp3` when that file exists, and prints a note and passes when it does not. The file is copyrighted audio and git-ignored (`server/tests/fixtures/*.mp3`); never commit it. Any Deezer `preview` download works as the fixture. All other MP3 tests build synthetic streams.
- **The machine may run other services**, including other Vite processes. Stop only what you started, by PID; never `pkill -f vite` or similar.
- Deployment settings are environment variables only: `ND_BIND` (default `127.0.0.1:4810`), `ND_DATA_DIR` (default `data/`, for previews, the cookie key and SQLite), and `ND_PUBLIC_URL` (optional; shared by the server and Vite). A variable that is set but blank uses its default. `RUST_LOG` remains the tracing filter, default `info,tower_http=debug`. The launch date is fixed at 2026-10-01 and production storage is SQLite.
- **What the songs are:** the server logs each pick at `info` when it is made (`picked the section's song for the day day=… section=… track_id=… title=… artist=…`) and each load (`loaded a song from … title=… artist=…`); `curl http://127.0.0.1:4810/api/admin/state` lists today's four answers, making the picks if they are not made yet.
- **Deezer cache on disk:** `<data_dir>/audio/<track_id>.mp3` and `.json` are reused on every start, so restarts (bacon restarts the server on each source change) cost Deezer nothing. Delete the two files to fetch again. Random mode caches every song it draws, so the directory grows towards the whole pool (about 480 kB a song: some 330 MB for 687 songs).
- **The data directory:** `data/` by default. A deployment puts the entire directory on persistent storage with `ND_DATA_DIR` in the server environment (absolute, or relative to the working directory). It holds the preview cache, `secret.key` and `needledrop.db`. Copy the existing directory's contents when moving it to keep the song pool, picks and game records. The cookie rename from `gts_player` to `nd_player` gives existing browsers new player IDs.
- **The database:** `<data_dir>/needledrop.db` (SQLite): the song pool, every player's games, the daily picks and the day offset. The server creates it at startup, brings its schema up to date (version 4; an older database gains the `games`, `picks`, `clock` and `random_games` tables and keeps its songs) and, when the pool has no song at all, adds the six seed songs. Delete the file to start again from the seed; that also forgets every game and pick. To forget the games only: `DELETE FROM games`; the admin's Reset to day 1 deletes games and picks and keeps the pool. A file the server cannot use (not a database, a schema newer than the server knows, tables of another shape) stops it at startup with a message and is left as it was. Any SQLite client can read the file; `node:sqlite` in the dev shell's Node works. Tests never touch it: they use the in-memory store or a database in a temporary directory.
- **Filling the pool from playlists:** `node scripts/add-playlist.mjs <playlist id or deezer.com address>… --genre pop [--genre rock] [--min-rank n] [--dry-run] [--api origin]` against a running server (default `http://127.0.0.1:4810`, or `ND_API`; on the host that is the deployed service, reached without Authelia because it is loopback). It reads the pool, fetches the playlist from Deezer (`/playlist/{id}/tracks`, 100 a page), leaves out tracks that are not `readable` or have no `preview` (the check the add route does not make), and adds the rest with `POST /api/admin/songs`. **The add route does not refuse a duplicate**: it answers 200 and replaces the genres, so the script settles duplicates itself. A song that is in the pool, as the same track or as another release of the same title and artist (a key close to `game::normalize_title`), is never added twice; it gains the genres it lacks and keeps the ones it has. Without `--genre` the songs go into General only. `--min-rank` leaves out tracks below a Deezer `rank` (600000 kept the well-known half of the dance playlists). Each new song costs the server one Deezer request from its budget of 40 per 5 s, so adds are 400 ms apart; Deezer's quota error, a 502 and a 429 are waited out (6 s, three times). It prints what each playlist gave (added, given a genre, already there, no preview, failed) and the pool's totals before and after, and exits 1 if anything failed. Run `--dry-run` first and read the titles: a playlist's name says little about what is in it.
- **`just server` does not reload.** Only `just dev` (bacon) rebuilds and restarts the API when `server/src` or `server/Cargo.toml` changes. A server started with `just server` runs the binary it was started with until someone restarts it, so check which one is running before expecting a change to be live.

## Conventions

- Conventional-commit messages (`feat: …`, `fix: …`, `chore: …`).
- **No AI attribution in commits, ever.** No `Co-Authored-By` trailer for Claude, Claude Code or any other assistant, no `Claude-Session:` trailer or other session link, no "Generated with …" line. This overrides any tool default that adds them. The message is the subject and body only, authored as the repository owner.
- One commit per completed task, **not one per edit**. Follow-up corrections to the same piece of work go into that work's commit (amend or squash while it is unpushed) rather than a string of small commits. Push only when asked.
- Build tasks are delegated to subagents. The orchestrating agent briefs each one, reviews the diff, runs the checks and commits; subagents do not commit.
- Every task ends by updating the Progress section below, so this file and the git history never disagree.
- An agent cannot hear audio, and headless Chromium has no audio output, so anything about how a clip sounds (audible, click-free, right length) must be checked by the owner by ear in a real browser. Say so instead of claiming it works.
- Be gentle with Deezer (see the rate limit below). Do not loop over the API to explore; cache responses to a scratch directory and analyse them offline.

## Deezer facts worth not rediscovering

- `api.deezer.com` sends no `Access-Control-Allow-Origin`, so it must be called from the server, never from the browser.
- Rate limit: **50 requests per 5 seconds** per IP. Autocomplete needs the TTL cache.
- `/search/track`, `/track/{id}` and `/playlist/{id}/tracks` all work without authentication.
- `/playlist/{id}/tracks?limit=100&index=N` paginates; the response carries `total`. `limit=100` is the largest page used here.
- Preview URLs are signed (`…dzcdn.net/….mp3?hdnea=exp=…~hmac=…`) and **expire after about 15 minutes**. Download the MP3 once and cache the bytes; never store the URL.
- Previews are 30 s, 128 kbps CBR, 44.1 kHz MP3: a 10-byte ID3 header, then frames of about 418 bytes / 26 ms. A clip can be cut by slicing at frame boundaries; no transcoding or ffmpeg. The one preview measured (479,827 bytes) is an empty 10-byte ID3v2.4 tag plus exactly 1148 frames of 417/418 bytes: no Xing/Info frame, no ID3v1 trailer, no partial frame. That is **29.988 s, not 30**, so the last ladder step is "everything" rather than a full 30 000 ms.
- Tracks carry `title_short` — the title without "(Remastered …)" and similar — next to `title` and `title_version`. Use it for matching.
- A track that cannot be played has `"readable": false` **and** `"preview": ""`; in every playlist checked the two always went together. Filter on both anyway.
- **User playlists rot.** Old playlists point at track IDs that have since been withdrawn, so a large share of a playlist can be unplayable. Measured on 2026-10-01 from a US IP address (availability varies by country): `88551731` "All time hits" 51 of 139 playable (37%), `3564546242` "500 Greatest Hits of All Time" 193 of 494 (39%). Check a playlist's playable share before adding it.
- Playlist `title` is cut off at 50 characters by the API.
- Each track has a `rank` (Deezer popularity, higher = better known) that could filter out obscure tracks.

## Design direction

**Midnight listening room**, approved on 2026-10-01. The owner requested a complete replacement of the saturated sleeve UI with an OLED-black design while retaining the spinning record and needle. Read **DESIGN.md** for the maintained visual contract and token mapping. The old weekday palettes and `?sleeve=` overrides no longer affect the page.

### Palette and type

- True-black page `#000000`, graphite surfaces `#151515`, warm ivory `#F3EFE7`, champagne accent `#D8B983`, muted silver `#96999E`.
- The sky adds decorative tokens only: `--sky-warm` (`216 185 131`, the accent as light), `--sky-cool` (`58 86 156`, one deep blue), `--star-cool` `#C7D2E8` and `--accent-bright` `#E8D2A6` (a lit champagne control). The hazes stay at low alpha (0.3 at most, at the record's edge), so the field still reads as black. None of them carries text.
- Decorative borders `#303030`; the search control uses `--control-border: #666666` for a 3.18:1 boundary against graphite. Ivory on black is 18.31:1; muted text on graphite is 6.39:1; dark ink on champagne is 9.95:1.
- Self-hosted Bricolage Grotesque: regular-width weight 600 question, condensed weight 800 revealed song title, 400/600 body and labels. Input text stays 16 px or larger. Clip times use tabular numerals.

## Roadmap: sections, song database, players and admin

Agreed with the owner on 2026-10-01. This is the specification for tasks 10–14 in Progress. Items marked *(assumed)* were not asked; they are the builder's defaults and the owner may overrule them.

### Sections and the daily pick

- Four sections, each a separate seven-attempt game per day: `general`, `pop`, `rock`, `hip-hop` (the slugs used in URLs, the API and the database).
- Every song in the database is in the General pool. A song may also carry **any number of genre tags** (none, one or several of pop / rock / hip-hop) and is in the pool of each genre it is tagged with.
- **No song is the answer in two sections on the same day.** Picks are made in a fixed order — Pop, Rock, Hip-hop, then General — and each excludes the songs already picked that day, so playing a genre section never spoils General.
- A section does not repeat a song until its pool is used up *(assumed)*: prefer songs not picked in that section since the pool was last exhausted, and never yesterday's when there is another choice.
- Picks are stored (day, section, track), so a restart keeps the day's songs. They are made lazily, the first time a day is asked for.
- **The daily pick checks that the preview is available.** It runs once per section per day (and again on an admin re-roll), and it has to fetch the track and its preview to play it anyway, so the check costs nothing extra. If Deezer says the track has no preview (`readable: false` or an empty `preview`), that song is skipped for the day and another is drawn. The add endpoint stays unvalidated (see Admin), so this is the safety net for songs that were added unchecked or withdrawn later.
- Only "this track has no preview" skips a song. Deezer being unreachable or over the request budget is not a verdict on the song: the pick fails with 502 `upstream` and is retried, as the song load is today, rather than burning through the pool *(assumed)*.
- A skipped song stays in the database and is tried again on later days; the day it last failed is recorded and shown in the admin pool list so the owner can remove it *(assumed)*.
- A section with no pickable song after the day's exclusions and skips answers with an error the UI shows as "No song today" *(assumed)*.
- **Seed:** six songs, two per genre, in `server/src/store/seed.rs` (`SEED_SONGS`; chosen on 2026-10-01; that day each was `readable` and its preview downloaded as a full 479,827-byte MP3): Pop — "Billie Jean" (Michael Jackson, `4603408`), "Toxic" (Britney Spears, `15391618`); Rock — "Bohemian Rhapsody" (Queen, `4091937401`), "Back In Black" (AC/DC, `92720046`); Hip-hop — "Lose Yourself" (Eminem, `1109731`), "Juicy" (The Notorious B.I.G., `3616616`). The server inserts them at startup, through the `Store` trait, when the pool has no song at all, so later removals stick (removing every song brings the six back at the next start). A database had been built by hand from the old `server/seed.sql`, with the same two tables and no schema version; the SQLite backend adopts such a file as schema version 1 and keeps its rows.
- **The database stores track IDs and display metadata only — never audio or preview URLs.** Preview URLs are signed and expire in minutes; the MP3 is downloaded when a song is picked for a day and cached under `data/audio/`, as today. With the seed alone, each genre alternates its two songs and General picks one of the three the genres did not take that day.
- The former `track_id` and `playlists` settings are gone: picks come from the database.
- *Built in task 12* as written above, with these details: a pick is stored only after its song has been loaded, so the check is the load; a song found in the disk cache counts as playable without asking Deezer; "no preview" also covers a preview body that is not an MP3 and a track Deezer no longer knows; a failed check is cleared the next time the song is picked and plays; General waits behind a genre section that is stuck on a Deezer failure (they share the one Deezer); a re-roll would rather repeat yesterday's song than draw the replaced one again.

### Storage

SQLite, one file under `data_dir` *(the SQLite crate is the builder's choice; it must not need a system library or a separate service)*. It holds the songs and their genres, the picks, the players, their games and the day offset. The parsed-preview disk cache in `data/audio/` stays as it is. Built: the trait, both backends and the contract suite, on rusqlite with its `bundled` SQLite, with the song operations (task 10), the players' games (task 11) and the picks and the day offset (task 12). "The players" turned out to need no storage of their own: a player is an ID in a cookie and exists in the database only as the games stored under it.

**The database sits behind one abstraction**, so MySQL, Postgres, a document store or Firebase can replace SQLite later by writing one new implementation and nothing else (asked for by the owner on 2026-10-01):

- A `Store` trait (async) in its own module is the only way the rest of the server touches persistent data. Handlers, the pick and the stats hold an `Arc<dyn Store>`; no SQL, connection type or database error type appears outside the implementation.
- Its methods are **domain operations, not queries**: list / add / retag / remove songs; get a day's picks and the pick history of a section; save a pick; load and save a player's game; list a player's games in a section (all of them: an unfinished game on an earlier day is a missed day, which the stats need to see); delete everything a player has; delete games by day and section; get and set the day offset; wipe picks, games and players. They take and return plain domain types (`game::GameState`, track IDs, dates).
- **Logic stays in Rust, above the trait.** Choosing the pick is a pure function over the pool and the history; stats are computed from the list of games. A backend only fetches and stores, so nothing depends on joins, aggregates or SQL dialect — which is what makes a document store possible.
- The only atomicity a backend must provide is single-record: "save this pick unless the day and section already have one" (two requests at midnight must agree on the song), and "replace this game". No multi-table transactions. That two moves of one player do not both build on the same stored game is settled above the trait, by a lock in the server (`player::MoveLocks`), not by a conditional write.
- Two implementations from the start: `SqliteStore`, and an in-memory one for tests. One shared test suite runs against both and is the contract a future backend has to pass.
- Production uses SQLite; the in-memory backend is kept for tests.
- The seed songs are inserted through the trait from a backend-neutral list (`store/seed.rs`), so every backend is seeded the same way. The schema belongs to the SQLite backend (`store/sqlite/001_songs.sql`).

**Stats are derived from the stored games, not kept as counters.** Re-rolling a pick or resetting the clock deletes games, and derived stats then correct themselves.

### Players, streaks and stats

- The cookie carries only a random anonymous player ID (HttpOnly, long-lived, refreshed on each visit); every game and stat is in the database. Reasons: four games do not fit in one 4 kB cookie (one worst-case game is 2.7 kB), and server-side streaks cannot be forged. The old `gts_daily` cookie is ignored. *(Built in task 11, for the one section there is; the details are under **API** near the top of this file.)*
- **One streak per section.** A streak is consecutive days **won**: a loss or a missed day resets it to zero.
- Recorded and shown per section: current streak, best streak, games played, win rate, and the guess distribution (which of the seven attempts the win came on).
- **Clear my data:** a button on the player page, behind a confirmation. It deletes that player's games and stats, today's attempts included, and issues a new anonymous ID. The day's songs do not change. *(Built: the route in task 11, the button and its confirmation dialog in task 13.)*

### The day clock

- The effective day is the real UTC date plus a stored offset in days, **for the whole server**: every player moves together, exactly as at a real midnight. Everything that says "today" (picks, games, streaks, the day number) uses the effective day.
- **Simulate next day** adds one to the offset.
- **Reset to day 1** sets the effective day back to `launch_date` and deletes all picks, games and players. **The song database is kept.**
- *Built in task 12* (`Daily::days`, `next_day`, `reset`; the offset is one record in the store). There are no player records to delete: a player is the games stored under an ID, so after a reset every browser keeps its cookie and has no games.

### Admin

`/admin` in the web app, and `/api/admin/*` on the server. **Unprotected for now** by the owner's choice; it must be protected or disabled before any public deployment, because it can show the day's answers and wipe every player's data. The anti-leak rule applies to the player routes, not to these.

Admin API (route names are a proposal; the behaviour is the requirement). All of it is built as written here (tasks 10 and 12); the exact shapes and error codes are under **Admin API** near the top of this file:

|---|---|
| `GET /api/admin/state` | Real date, offset, effective day and day number, and today's pick for each section. |
| `GET /api/admin/songs` | The pool: track ID, title, artist, genres, and the day its preview last failed the daily check, if it has. *Built as a searched and paged route (task 14): the owner expects hundreds of songs and asked that the page never load them all.* |

- For server work, what to know about the code as it stands:
  - The store. Handlers reach it through `AppState::store()` (a `&dyn Store`) and turn a `StoreError` into 500 `internal` after logging it (`routes::store_failed`). "Not there" is `None` or `false`, never an error. The trait's signatures are in the reference block below.
  - Adding to the store takes four steps: a method on the trait in `store/mod.rs` (a domain operation over plain types, atomic for one record); its implementation in `memory.rs` and in `sqlite.rs`; when it needs a table, a new numbered script in `store/sqlite/` appended to `MIGRATIONS` (never edit an existing script, because existing databases have already run it); and cases in `store/contract.rs`, with their names added to the list inside `contract_tests!`. `BrokenStore` in `testutil.rs` implements the trait too and needs each new method, and so do the wrapping stores (`testutil::Unhurried`, and the ones in `routes::tests` that pause in the middle of an operation, for the tests of simultaneous requests).
  - The SQLite backend has one connection, so a trait method is atomic by being one closure passed to `SqliteStore::run`. `save_pick` is an `INSERT … ON CONFLICT DO NOTHING` followed by a read, as `add_song` is.
  - **The day** comes from `app.today()` (`Daily::today`: the clock's real date plus the stored offset), read once per request and passed down. `game.rs`, `stats.rs` and `pick.rs` have no clock on purpose. Tests pin the real time (`testutil::TODAY`, `harness.clock.set(day)`, `harness.clock.advance_minutes(n)`); nothing in a test should read the wall clock. Real time, for random mode's idle rule, is `app.now()` (seconds since the Unix epoch), read once per request; the day offset does not move it.
  - **A request and the song it uses.** `app.song(section, day)` can be slow (a pick, a download) and is called before any lock. What a handler then reads or writes about the games must happen while `Daily::stands(&playing)` is held, because a re-roll or reset replaces the song and deletes its games: lookers go through `routes::standing_song` (which fetches the new song and looks again), a move takes the player's move lock first, then `stands`, and answers 409 `changed` when the song is gone. The admin's changes take the write side and never the move lock, so there is no deadlock.
  - **Picks.** Made lazily by `Daily::song`, in `pick::PICK_ORDER`, stored only after the song loaded. `Section::ALL` is the tab order (General first), not the pick order. A song that leaves the pool keeps its picks. `Daily::reroll` only deletes (games first, then the pick) and remembers the replaced song in memory; the next `song` call draws.
  - **Game storage.** A game exists in the store only once a move has been made; "no game" is a fresh game, and handlers apply `.for_day(today)` to whatever comes back. Stats need no attention after a re-roll or reset, being derived.
  - `Track::is_playable()` is the readable-and-has-a-preview check. Every Deezer API call goes through `Deezer::get_json` and counts against the 40-per-5-s request budget, admin routes and picks included; a first-of-the-day pick of four uncached songs is four API calls and four downloads.

  - `rand` 0.10 makes the player IDs (`rand::random::<u128>()`) and the picks (`rand::rng()`, the `RngExt` trait; its names differ from older examples). A generator must not be alive across an `await`.

  Rules the routes follow, which new routes must keep:
  - Serve only `Mp3::prefix` output, never the downloaded bytes: `parse` is what strips the tags, and a tag can carry the title.
  - Who is playing comes from `player::known_player(&jar)` and from nowhere else; a request without a usable cookie is a new player (`PlayerId::generate()`), and a response that shows the game sets the cookie with `player::remember`.
  - `today` is the server's day (`app.today()`), read once per request. The game, stats and pick modules have no clock on purpose.
  - The song comes from `app.song(section, today)`, before any lock; the games are read and written only while `Daily::stands` holds for that song.
  - Game in: `Store::game` or `Store::games`; nothing stored for today → `GameState::new(today)`; then always `.for_day(today)`. A visit stores nothing.
  - A move is read, applied and saved under `app.move_locks().lock(&player)` and then the standing guard, with nothing slow inside.
  - A `StoreError` goes through `routes::store_failed` and a `DailyError` through `routes::daily_failed`: logged, a fixed message, never the reason.
  - A guess's `TrackMeta` comes from Deezer by ID (`Deezer::track_meta`), never from the request body.
  - Random mode has no day and no standing guard: its game is one record per player, and what keeps a request about one song is the `round`, checked again under the move lock together with whether the session is still going (`is_over(now)`, with the `now` read at the start of the request).
  - Random mode's pool is changed only by `POST /api/random/start`, under the move lock, on the record as read there, and the change never draws a song or touches `active_at`. Anything that replaced the song being played on a change of genre would be the give-up shortcut the owner refused.

- **`/admin` and `/api/admin/*` have no app-level authentication.** The deployed reverse proxy must enforce Authelia on both paths, and the Rust server must stay on loopback.

- **A browser the server has not met is a different player to each request it sends at once.** Every answer that sets the cookie issues its own ID to a request that came without one, and the browser keeps the last. For the daily game that is harmless (a look stores nothing). A random session is stored by its start, so the client lets the page's first requests finish before it starts one. If a cookie-less request is still answered later than the start (a refresh racing it), the game is under an ID the browser no longer has: the next request gets 404 `no_game` and the page starts another session, saying so.
- A change of genre is a `POST /api/random/start`, so it shares the deployment's draw limit (1 per second, 10 extra at once) with real starts and Next song. A player flicking through the picker can be answered 429 `rate_limited`; the picker then shows the genre that stands and the page shows the message.
- The genre in the view and in the picker is where the next songs come from. After a change in the middle of a song, the song on screen is still one from the old pool until it is over.
- The recent list (50 songs) is one list across genres. A genre with fewer playable songs than that is gone round in a fixed order once all of them are recent, and a genre the day's picks have emptied (possible only with a tiny pool) answers `no_song` until a re-roll or the next day.
- Choosing a genre does not extend the session. A player who does nothing but change genres for half an hour has the session end under them.
- If another tab changes the genre between a Next song's draw and its turn under the move lock, the song already drawn from the old pool is played; the session keeps the new pool for the songs after it.
- A change of genre in a session that is going loads the session's song first (for the view). If that song can no longer be loaded (502), the change is not made.
- "Check again" on "No song to play" with no song on screen sends the genre the picker shows. After a first load that found nothing, the page cannot know the stored choice and shows All, so that press replaces a stored genre with All.
- A failed change of genre while a song is open is reported in the move-error line above the tries, while the picker is below them: on a phone the line can be off screen (it is `role="alert"`).
- In the side layout the reveal's focus order is Next song, the genre, the Deezer link, Play, while the genre is drawn last.
- The page's own handling of a change of genre (`choosePool` in `lib/game.svelte.ts`) has no unit tests, like the rest of that store; it was checked in headless Chromium with a script that was not kept.
- One random game per player, so every tab of a browser plays the same session. A tab that is behind catches up when it becomes visible. Until then its move is made on the game as it stands when the song is still the same, and gets 409 `changed` when another tab has moved on to the next song.
- A random session's idle time counts writes only. A player who listens to one song for half an hour without a skip or a guess has their next move refused and gets a new session; the song they were on is lost. Accepted: a look that extended the session would be a write on every visit.
- The line "That session ended after a while away. This is a new one." is also shown when another tab had already begun the new session and this one only joined it.
- The first visit to Random in a session logs a 404 in the browser's console: the look that finds no game, before the start. The look comes first on purpose: the deployment limits starts per connecting address, and a look costs none of that.
- No test proves the move lock in `POST /api/random/start`: the test of two simultaneous starts fails without the second look under the lock, but passes without the lock itself, because two identical starts converge. What the lock is for, a late start overwriting a move made in the session another tab has just begun, would need a store that pauses.
- Random mode's draws and loads take the same lock as the daily picks (`Daily`'s `work`), so players' next songs queue behind each other and behind a pick in progress, each for as long as a Deezer lookup and a 480 kB download. Fine for a few players at once. Each uncached draw is also one Deezer API call from the shared budget of 40 per 5 s.
- Only the picks that stand when a random song is drawn are left out. A pick made later that day (a re-roll, a section that was stuck) can be the song someone is on in random mode, or one they have just been shown the answer of.
- A random song that can no longer be loaded (it left memory, its disk cache is gone and Deezer has withdrawn the track) answers 502 on every look, and the player cannot ask for the next because the song is not over. Half an hour without a move (the session ends) or Clear my data gets them out.
- When a section has no song on a day (a small pool), every random draw gives the sections their turn again: a few store reads, and a line in the log.
- Random games are never pruned: one row per player who ever started a session (under 4 kB), and a client that posts `start` without keeping the cookie makes a row per request. The deployment's nginx allows one draw per second per connecting address.
- Reset to day 1 deletes the random games, the longest runs with them.
- At 320×568, Skip ends about 1 px below the fold on every tab (measured in task 24, 568.9 px, with and without the genre picker; the "7 px above the fold" in Design direction was measured before the fifth tab).
- At 320×568, Next song starts about 19 px below the fold when the revealed title takes two lines; from 360×740 it is fully on screen. Also at 320×568, on every tab, the search list opens above the field and is cut off by the scrolling game column, so its top results can be reached with the arrow keys only (seen in task 22, there since the game column began to scroll in task 17; not fixed).
- An open page learns of a re-roll only from its next request. If the player has used tries there, the next move or refresh shows the fresh game (409 `changed` only when the two collide). If no try was used, nothing on the page changes, and the clip in memory is still the replaced song's first 0.1 s: the clip's address (`?t=<day>-<attempts>-<status>`) is the same for both songs. The first move or a reload mends it. A song ID or version in the game response would let the client tell; the anti-leak rule forbids the Deezer ID, so it would have to be something opaque.
- A page left open over midnight makes its next move in the new day's game: the server applies the move to today, and the page then says the day has changed and shows that game with the try used. Nothing polls for midnight; the page asks again only when the browser tab becomes visible or a request is made.
- There is one audio player with one decoded clip, so every tab switch fetches the section's clip again (a few kB early in a game, about 480 kB for a finished one). Text typed into the search is not kept across a switch.
- `lib/game.svelte.ts` has no unit tests (it needs the Svelte compiler and `fetch`); its handling of the server's answers was checked in headless Chromium with scripts that were not kept. The same goes for the admin page's two stores (`desk.svelte.ts`, `finder.svelte.ts`) and its components.
- The admin page does not watch the server. It shows the state it was last given: a midnight, a pick made by a player's request, or a change made in another admin tab shows after Refresh. A section that is `unavailable` is not asked about again by itself; "Try again" does it.
- The pool search shows the first 25 songs that match, in the order artist, title, and there is no second page, by the owner's choice. The list behind "show them" (failed preview checks) has the same cap and no text to narrow it with; removing songs brings the rest up.
- After an add the pool search is set to the new song's track ID. The server matches the text against titles, artists, albums and track IDs alike, so now and then a second song whose ID or title contains those digits is listed with it.
- "In the pool" on a Deezer result is what the server said when that search was answered. A song added or removed since (in another tab, or through the pool search while the list was open) shows it wrongly until the search is typed again; the add itself is safe either way, because the route replaces genres for a song that is there.
- Changing the genres of a song that someone else has just removed adds it again: the route cannot tell a retag from an add.
- When adding, a new song's genre boxes start as they were for the last song added on that visit, which suits adding a batch of one genre and can put a song in the wrong section if the boxes are not looked at. The line under them says where the song will play.
- The admin page has been seen only in headless Chromium, at 1440×900 and 390×844, with at most 25 rows on screen. Unverified: Safari, Firefox, a physical phone, a screen reader.
- The player's JavaScript is two files since task 13 (the Svelte runtime became a shared chunk when the admin page was made a dynamic import), 109.37 kB together since task 14: the shared chunk also carries the runtime helpers that only the admin page uses, about 2.5 kB that a player downloads for nothing. `main.ts` uses top-level `await` (Safari 15+), and the confirmation uses `<dialog>` (Safari 15.4+).
- A tab's state is told to a screen reader in its name ("Pop, won") and again in its tooltip text; that repeats, harmlessly.
- A song that was Pop's answer yesterday can be General's today: "no repeat" is per section, by design. (A database started from the six seed songs alone also makes every answer one of six and each genre alternate its two; the deployed pool has 687 since task 21.)
- The pool filled in task 21 is what Deezer's editors put in their playlists, unread: "Rock Hits" and "Rap Bangers" are recent releases, "East Coast Essentials" and "GTA West Coast Classics" go deep, and no rank floor was applied to rock, hip-hop or the three pop playlists. Some answers will be hard to guess from any clip. Every song has exactly one genre except three that the pop playlists share with the hip-hop ones, which are both.
- About a quarter of the tracks in Deezer's own editor playlists had no preview from this server's address (US), well-known songs among them ("Smells Like Teen Spirit", "Zombie", "Dream On"): the playlist points at a release that is not available here. `scripts/add-playlist.mjs` leaves them out; it does not look for another release of the same song that would play.
- `GET /api/admin/state` has a side effect: it makes the day's missing picks, and so does every admin route that answers with the state. Opening the admin page after midnight is what draws the day's songs if no player came first.
- A re-roll remembers the song it replaced in memory only. If the server restarts between the re-roll and the next request for that section, the new pick can be the same song again.
- A pick that stands is never replaced behind the players' backs. If its song cannot be loaded any more on the same day (the disk cache is gone and Deezer has withdrawn the track), the section answers 502 until the owner re-rolls it; the log says so.
- General cannot be picked while a genre section is stuck on a Deezer failure: it waits behind it and answers 502 too, even if its own song would be in the disk cache.
- `GET /api/today` says `pending` from the pool alone, without checking previews, so a section it calls `pending` can still turn out to have no song when its game is asked for.
- Moving the clock forward with Simulate next day and then waiting for real midnight moves it again: the offset is added to the real date. Reset to day 1 is the way back.
- The standing lock (`Daily::stands`) and the pick lock work inside one server process, like the move lock.
- A player who was in the middle of a game when the server is updated from before task 11 starts that day again: the old `gts_daily` cookie is not read. The song is also a different one, since the picks replaced `track_id`.
- Games are never pruned. Every player who makes a move leaves one row per section and day for good, and a client that sends moves without keeping the cookie makes a new player, and a row, with every request. The server does not limit that; the deployment's nginx allows one guess per second per connecting address (task 20). The rows are small (about 100 bytes for a game of skips, 2.7 kB at worst).
- The deployment's rate limits count the address that connects to nginx. The site is behind Cloudflare, so that is one of Cloudflare's addresses and not the player's: players who arrive through the same one share a limit, and one client's requests can be spread over several. Counting players would need nginx's `set_real_ip_from` for Cloudflare's ranges with `real_ip_header CF-Connecting-IP`; the owner decided against it on 2026-10-01.
- The stats are worked out from all of a player's games in the section on every `GET /api/daily/{section}` and every move: one query and a pass over the list. Fine for years of daily play by one player; if it ever is not, store a summary per game rather than counters.
- The move lock (`player::MoveLocks`) works inside one server process, which is all there is. Two server processes over one database could let two simultaneous moves of a player share a try; that would need a conditional write in the store.
- Clear my data cannot revoke the old ID: a saved copy of the old cookie still works, as a player with no games. Likewise there is no way to move a player to another browser.
- Changing the cookie key (deleting `<data_dir>/secret.key`) turns everyone into a new player and leaves their old games in the database, unreachable. `DELETE FROM games` clears them.
- `stats.winPercent` is a whole number; the client can compute a finer rate from `won` and `played`.
- A section's game needs its song, not only the player's game: with Deezer unreachable and the song not in `data/audio/`, `GET /api/daily/{section}` answers 502 `upstream` (as do the audio and guess routes) until a pick and load succeed. They are retried on a request at most every 10 s. Once the day's songs are in memory or on disk, Deezer being down only breaks search and guesses whose track is not in the metadata cache; skips keep working.
- The request budget (40 Deezer API calls per 5 s, shared by all players) turns searches beyond it into 502 `upstream` rather than queueing them. The client should treat a failed search as "no results for now", not as a fatal error.
- Search fetches 25 Deezer results and de-duplicates afterwards, so a query whose top 25 are mostly releases of one song returns fewer than 8 rows.
- Numbers that are whole serialize with a decimal point (`"clipSeconds":1.0`, `ladder` `[…,1.0,3.0,…]`). They are the same numbers to JavaScript.
- The track metadata cached in `data/audio/<id>.json` is never refreshed; delete the file to refetch.
- The tower-http `fs` / `compression-gzip` features are in `Cargo.toml` but unused until the production static-file serving exists.
- Playlists are no longer the plan for the daily pick (the song database is; see Roadmap), but they remain a possible source for a bulk import through the admin API. What was learnt: the pool is weaker than hoped. The original candidate `88551731` was dropped (37% playable). - The shortest clip is bigger than "a few hundred bytes": `prefix(100)` is 8 frames (4 for 100 ms + 4 padding), 3,343 bytes on the real preview, about 209 ms of audio. The padding is what makes the cut safe to decode; the client must trim to the exact duration, and a determined player can hear ~0.2 s instead of 0.1 s on the first turn. Accepted.
- A preview is 29.988 s, so on the last ladder step the client must clamp playback to the decoded buffer's length rather than assume 30 s.
- Matching drops every `(…)` and `[…]` segment, so "(Remix)" and "(Instrumental)" variants count as the same song as the original, and titles differing only in a bracketed part ("Da Doo Ron Ron (When He Walked Me Home)") lose it. Checked offline against the 2,710 distinct tracks cached during playlist research: 37 key collisions, all the same song in another release, no false merges.
- `jiff` is the date crate, with its `serde` feature on (`civil::Date` serializes as `"YYYY-MM-DD"`). `rand` is 0.10 and `reqwest` is 0.13, whose APIs and feature names differ from older examples (`rustls`, not `rustls-tls`; `query` is its own feature).
- reqwest's rustls backend builds `aws-lc-sys` and rusqlite's `bundled` feature builds SQLite, both C code, so the first server build takes one to two minutes.
- **The admin API has no app-level authentication.** `/api/admin/*` can reveal answers and mutate the day, games and pool. The mainframe reverse proxy applies Authelia to `/admin` and `/api/admin/*`; a direct request to port 4810 bypasses it, so bind the server to loopback.
- `POST /api/admin/reroll` does not look at the content type and treats an empty body as "all four", so a stray POST re-rolls everything and deletes the day's games.
- Removing every song from the pool brings the six seed songs back at the next start: the rule is "the pool is empty", and nothing records that a pool was seeded before.
- A song's stored title, artist and album are never refreshed from Deezer, and a retag keeps them. Remove the song and add it again to refetch them.
- `POST /api/admin/songs` answers 200 for a new song and for a retag alike.
- The admin search shows at most the 25 tracks Deezer returns for the query; there is no paging. The pool search reads the whole pool from the store on every request and filters it in Rust, which is fine for thousands of songs and would want an index, or a store operation, far beyond that.
- `songs.added_at` is in the SQLite schema (inherited from the hand-built database) but the server neither reads it nor exposes it; the pool is listed by artist and title, not by when a song was added.
- The SQLite backend cannot hold a track ID above `i64::MAX`: adding one is a store error (500), where the in-memory backend accepts it. Deezer's IDs are around 2³².
